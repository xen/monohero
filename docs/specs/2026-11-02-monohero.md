# Monohero 0.1

## Goal
A local Rust CLI serializes authorized workflows in durable, independently named FIFO queues, without model polling or coordinator messages.

## Design
One explicitly started Unix daemon, private state directory, Unix socket, SQLite job journal. FIFO is the order in which the daemon commits submissions. Each queue has one worker; different queues run concurrently. A job contains an explicit executable/arguments, working directory, deduplication key and optional completion executable. The daemon owns execution, so closing the submitting chat does not cancel jobs. Wait subscribes to completion using a blocking socket, with no status polling.

## Boundaries
macOS/Linux, one local user and host. No remote locking, GitHub credentials, deployment policy bypass, implicit shell, automatic chat injection, or automatic retries. Agent clients must supply an authorized executable workflow; Monohero is not an LLM. Store no inherited environment in the journal: jobs inherit daemon environment. Logs may contain command output and are private. No install or modification of other projects as part of this release.

## Failure handling
SQLite commits before acknowledgement; queue-scoped deduplication survives restart. On restart running jobs become interrupted and block their queue pending explicit resolution. Queued jobs remain durable. A daemon ownership lock is inherited by child processes to prevent a replacement daemon overlapping a surviving job. Failed jobs block their queue too, allowing inspection of partial external changes. Resolving a blocker acknowledges inspection; it does not retry. New work gets a new key and joins the tail.

## Verification
Black-box CLI tests: FIFO, independent queues, duplicate submissions, wait delivery, failure barrier, restart persistence, interrupted-job barrier, surviving child exclusion, executable failure, durable completion result. cargo fmt, clippy, tests and release build. No claims that an arbitrary Codex/Claude UI is automatically resumed. Integration instructions must explain detached submit + ending the turn, optional explicit completion callbacks, and one blocking wait where host supports it.
